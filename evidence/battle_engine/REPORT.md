# Function-evidence pilot: the battle engine

Branch `evidence-pilot` (from `battle-xcheck` d78bb44). Tools: `tools/evidence/` (README there). The shared files of
the lockstep work (`src/port/xcheck.cpp`, `tools/battle_xcheck.py`, `tools/ares_ref/*`, `src/port/Engine.cpp`,
`patches/game/20-fragment-battle_engine.patch`) are used as they are; nothing in them or in the game sources changed.

Files here: `coverage.md` (numbers, per file, pointer tables, functions with several runtime callers, runtime edges
the static graph lacks), `records.md` / `records_reviewed.json` (24 reviewed records), `reviews.json` (their
hand-written part). The full per-function file (all 2055 records, 3.5 MB) is regenerated by `analyze.py`.

## What was built

1. **Static call graph** (`callgraph.py`): every battle-engine file compiled with its own flags to -O0 LLVM IR;
   direct calls, address-taken functions, and indirect calls resolved through the pointer tables the function reads.
   Battle engine: 2055 functions (318 `func_`), 8139 call + 381 table + 422 ref edges, 14 pointer tables
   (`gMoveEffectHandlers` 34 handlers, `sBattleSceneStateRowTable` 51, the move-animation start/end tables, the
   particle descriptors). 4 dispatchers call pointers stored at run time (`BattleScene_TickStateCallbacks`,
   `BattleAnim_UpdateParticlePool`, `BattleAnim_UpdateEffectCallbacks`, `BattleAnim_DrawEffectCallbacks`): the
   runtime trace fills those in (194 runtime-only edges). Runs in 5 s; the whole decomp (351 files, 7474 functions,
   553 `func_`, 102 tables) in 16 s.
2. **Instrumented build** (`cmake/evidence.cmake` through `-DCMAKE_PROJECT_INCLUDE`, own directory
   `build-evidence`): the 49 battle-engine sources get `-finstrument-functions -fno-omit-frame-pointer
   -fno-optimize-sibling-calls`; `src/port/evidence/evidence_rt.c` (new) keeps a shadow stack and aggregates per
   (function, instrumented parent, return address) and per call path (10 deep), tagged with the battle context
   (scene phase, attacker side, user species and move, target species, gBattleDamage); a capped call sequence; the
   battle state (both BattleMonRuntime, both ActivePokemonState, BattleScene, gBattleDamage) at entry and exit of
   watched functions. Behaviour-neutral: seed 7 gives the reference battle's 71 events and the same random calls per
   function (117/22/130/6097/21); seeds 1 and 7 match ares event by event with this binary (105 and 71 events).
3. **Scenarios** (`run.py`, `watch.py`): the `battle_xcheck.py` battle with forced values. `watch.py queue` replays a
   baseline's values up to call k and forces one value there; `watch.py ares` runs the same battle in ares with the
   lockstep driver's case rules (`rule Battle_Random@Battle_CheckCriticalHit 34`) and reads its caller-tagged random
   trace; `watch.py diff` prints what each watched call changed. Port-only extra: `--moves` gives the player's
   Pokemon other moves (evidence_rt.c) for effects the rental teams lack.

## Records (24)

Verdicts: confirmed 16, unclear 6 (5 unnamed functions whose behaviour is now established, with a proposed name;
one PORT-changed function), name wrong 1, not reached 1. Highlights:

- `Battle_CheckCriticalHit` confirmed, and a **field-name bug** found with it: the crit threshold is computed from
  `gBaseStats[id].baseDefense`, which is the species' base **Speed** (gBaseStats = gSpeciesData - 0x1C; the
  `PokemonStats` stat names in `gb_data.h` are in reverse order). Forced crit roll 34 crits and 35 does not, in the
  port and in ares; 35 is exactly the Speed formula ((65 + 76) >> 2), Defense would give 29.
- `func_843708CC` (accuracy check): forcing 254 and 255 on a 100% move shows the redraw of 255 — Stadium removed the
  Game Boy's 1/256 miss (same in ares). Proposed `Battle_CheckMoveHit`; `func_843708A0` = `Battle_SetMoveMissed`,
  `func_84372670` = `Battle_ExecuteMove`, `func_84370B44` = `Battle_ApplyBurnAttackPenalty` (forced burn: Attack
  98 -> 49, same in ares), `func_84370ADC` = `Battle_SyncStatusToParty` (by code; its effect is outside the dump).
- `Battle_Effect_Counter` **name wrong**: not a table effect but a gate run before every move's damage (83 calls,
  every move); returns 1 unless the move is Counter. Proposed `Battle_TryCounter`.
- Effect handlers with state diffs: SecondaryStatusChance (forced burn), Confuse (unk_4C 0x80, 2-5 turns in unk_50),
  Sleep (a miss, then status 3), Heal (Recover +max/2), RaiseOwnStat (Swords Dance stage 7 -> 9, Attack x2), Haze,
  FocusEnergy (unk_4D bit 2, read by the crit check), Substitute (max/4 HP into unk_59). These also name 6 fields.
- Forced situations used: a crit (7 values bracketing the threshold), a miss roll on a 100% move and the 255
  redraw, a secondary burn; with injected moves a status move missing (Hypnosis) and a natural Fire Blast miss. Not
  forced yet: a status move failing on an already statused target, Recover failing at full HP.

## Effort per function

- Automatic (static paths, runtime callers and paths, context, counts): seconds for all 2055 functions; a full
  battle is ~50 s in the port, ~80 s in ares, two at a time.
- A forced scenario: 5-15 min to find the call to force (from the caller-tagged ares trace or the sequence log),
  then 15-50 s per run per side. One scenario usually serves 2-4 records (the crit runs gave 3).
- Review and writing: 3-6 min per record with the state diff at hand; ~10-20 min when a field layout had to be
  worked out (gBaseStats). The 24 records took about 2 hours including the scenarios.

## What blocked functions from being reached

1. **One battle setup.** `battle_xcheck.py`'s route always plays Poke Cup round 1 with the same rentals: the
   move-specific effect handlers (16 of 34) and most move-animation code need other moves. The port-only move
   injection reached 6 more handlers, but its evidence has no ares counterpart.
2. **Rule variants and modes not played:** the Game Boy-rules branches (`D_8438AC60[0] != 1`), attract mode
   (`BattleScene_TickAttractModeInput`), two-player input, Rest while statused (`Battle_ApplyStatStageMultiplier`),
   Counter itself, Metronome/Mirror Move, faint-replacement corners.
3. **State outside the dump:** static flags (`sBattleMoveFailed`, `sBattleCritFlag`), the party entries
   (TeamRoster), return values (`-finstrument-functions` gives none).
4. **PORT-changed functions** (32, 27 reached): where the port's hook decides (`BattleScene_IsActionSelectionTimerExpired`
   under PORT_XCHECK_COM), the run says nothing about the original logic.
5. **The autoplay bot** is not usable with this binary: its port side (`src/port/bot.cpp`) is on the `autoplay`
   branch, not in d78bb44. Merging `autoplay` into this branch would allow castle/leader battles with other teams.
6. Inlining: for inlined functions the return address names the caller's caller; the shadow stack gives the right
   parent (the records use it), so only entries from main code rely on the return address.

## Hook changes needed from the lockstep side

The ares binary used here is a copy of the lockstep work tree's current build (its `rule`/`mon` case file and
`ARES_REF_XCHECK_SYMS` caller names are not in d78bb44); records name the binary's sha256 prefix 939fff132f8cbc77.

1. Commit the case format on both sides (`PORT_XCHECK_CASE` / `ARES_REF_XCHECK_CASE`), and add a **one-shot rule**
   (by call index, not cycling), e.g. `rule Battle_Random@Battle_Effect_SecondaryStatusChance#0 0`: today ares's
   rule forces every call from that caller while the port queue forces one, so forced runs stay comparable only
   up to the next call from the same caller (the burn run diverges at the second Flamethrower).
2. The `mon` lines (moves, species, status, HP) on both sides: they replace the port-only `PORT_EVID_MOVES` and make
   every effect handler ares-checkable.
3. **An ares function-entry trace** for the battle engine: the driver has the symbol file and the host-hook list;
   one hook per function start logging (function, caller from RA) counts and paths would give the N64's own call
   graph and coverage to compare with the port's — the only independent check for the 32 PORT-changed functions.
4. ares: return values (v0 at the hooked return address) for a watch list, and the statics `sBattleMoveFailed`,
   `sBattleCritFlag` plus the TeamRoster party entries in the event dump.
5. The planned ares save state at the order screen (faster scenario runs).

## Scaling to the whole decomp (~7,400 functions, 541 `func_`, 33 asm)

1. **Static graph for everything now** (done in 16 s: 7474 functions, 102 tables, 389 functions with
   pointers stored at run time). Group functions into subsystems by file and graph component.
2. **Instrument by subsystem**, not all at once: `PORT_EVID_FILES` per fragment (the per-frame graphics code would
   dominate the counts otherwise). Use the same runtime; add SanitizerCoverage (`trace-pc-guard`) builds for cheap
   whole-game coverage and keep `-finstrument-functions` for the paths of the subsystem under review.
3. **Drivers per area:** battles with the lockstep cases (all moves, all rule sets, castle and cups through the
   autoplay bot once merged), menus and minigames with the recorded replays (`replays/*.rec`, `tools/tour.py`),
   GB Tower with its saves. Each driver run is reproducible (forced random, recorded input).
4. **Automatic triage** into: not reached (needs a driver), reached through one path matching the static graph
   (cheap review), several callers (check the name fits every use), runtime-only edges (dispatch to document),
   PORT-changed (ares needed). Review order: the 541 `func_` that are reached, then names whose state diff
   contradicts them (diff heuristics: which fields change), then the rest.
5. **Ares parity** for every subsystem through the function-entry trace (hook request 3), with fragment relocation
   handled as for fragment 51 (`gFragments[n]`).
6. The 33 asm functions have no C body in the port to instrument: cover them through their C callers on the port
   side and the ares entry trace.
7. Estimated effort: the automatic part is a few hours of machine time per subsystem; reviews at 3-6 min each are
   ~400-700 hours for everything by hand, so batch by scenario (one forced situation confirms several functions)
   and review the reached `func_` and the multi-caller functions first (~1,500 functions, ~100-150 hours).

## Reproducing

```
cmake -S . -B build-evidence -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PROJECT_INCLUDE=$PWD/cmake/evidence.cmake
nice -n 15 cmake --build build-evidence -j 4
tools/evidence/callgraph.py build-evidence /tmp/cg.json
tools/evidence/run.py /tmp/s7 --bin build-evidence/pokestadium --seed 7 --frames 30000
tools/evidence/watch.py queue /tmp/s7 /tmp/crit34.txt Battle_Random 0 34
tools/evidence/run.py /tmp/crit34 --bin build-evidence/pokestadium --seed 7 --queue /tmp/crit34.txt --frames 3800 \
    --watch Battle_CheckCriticalHit,Battle_ApplyDamageRandomFactor
tools/evidence/analyze.py /tmp/cg.json evidence/battle_engine /tmp/s7 /tmp/crit34 --reviews evidence/battle_engine/reviews.json
```
